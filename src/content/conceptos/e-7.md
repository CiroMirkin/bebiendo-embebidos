Una **prueba en banco** es probar el equipo real, sobre la mesa, contra **criterios de aceptación** escritos antes de empezar. Cada criterio dice qué se mide, cuántas veces y qué cuenta como falla, así que al final no hay discusión: pasa o no pasa. Las fallas que importan suelen ser intermitentes, de las que aparecen una vez cada tantas; por eso la prueba **repite**: 20 arranques, 200 ciclos, toda una noche. Un firmware de banco hace el trabajo repetitivo y anota los resultados.

## Por qué te importa

Un nodo que funcionó en tu escritorio dos veces no es un nodo probado. En el invernadero va a despertar 288 veces por día. Si la llave provoca un brownout en 1 de cada 100 encendidos, eso son casi tres reinicios diarios por nodo. En tu escritorio, con dos pruebas, no lo ibas a ver nunca.

La prueba en banco también es el momento de medir lo que en las lecciones anteriores quedó como "se mide en banco": cuánto tarda el sensor en estabilizarse, cuánto consume el nodo dormido, cuánto tarda el teclado en enumerar.

## Paso a paso

### 1. Escribir los criterios antes de probar

Un criterio de aceptación tiene tres partes: qué se hace, cuántas veces, y qué cuenta como falla. Para la llave del sensor del nodo:

| # | Criterio | Cómo se mide |
|---|---|---|
| 1 | Con el pin suelto, el sensor tiene menos de 0,1 V | tester, firmware de banco de la [E.5](/conceptos/e-5) |
| 2 | Prendida, el sensor tiene más de 3,2 V | tester |
| 3 | El tiempo de estabilización medido, en 3 sensores distintos | firmware (ejemplo 1) |
| 4 | 200 ciclos de dormir, prender, leer y apagar sin ningún brownout ni lectura fuera de 500 a 3000 mV | firmware (ejemplo 2) |
| 5 | Corriente del nodo dormido, anotada | tester con puente |

Escribirlos antes evita el sesgo de "funcionó, así que el criterio era ese". Si un número no se conoce todavía (como el tiempo de estabilización), el criterio es medirlo y anotarlo.

### 2. Por qué repetir

Si una falla aparece con probabilidad p en cada intento, la probabilidad de no verla en n intentos es (1 - p)ⁿ. Para una falla de 1 en 10:

| Intentos | Probabilidad de no verla nunca |
|---|---|
| 2 | 81 % |
| 20 | 12 % |
| 50 | menos de 1 % |

Para una falla de 1 en 100, ni 50 intentos alcanzan (60 %). Cuanto más rara la falla, más repeticiones hacen falta, y por eso las hace el firmware.

### 3. El firmware de banco

Es un programa aparte, que no va al equipo final. Hace una sola cosa muchas veces, cuenta las fallas y lo deja anotado en algún lugar que sobreviva a los reinicios:

- `RTC_DATA_ATTR` sobrevive al deep sleep, pero no a un corte de alimentación ([0.12](/conceptos/0-12)).
- NVS (`Preferences`) sobrevive a todo ([0.11](/conceptos/0-11)). Para contar brownouts es lo seguro, porque un brownout es un reinicio.

Imprimir los resultados en CSV deja pegarlos en una planilla o graficarlos.

### 4. Variar las condiciones

Una prueba en las mejores condiciones dice poco. Para un nodo a batería, se repite con la batería cargada y con la batería casi descargada. Para el sensor, con la sonda en tierra seca y en tierra mojada, y con más de un sensor. Si el equipo va a estar en un invernadero, la placa se prueba también caliente.

### 5. Anotar todo

Cada prueba deja una fila: fecha, versión del firmware (el hash de git), qué placa y qué piezas, condiciones y resultados. Cuando dentro de seis meses algo falle en el campo, esa tabla dice qué se probó y qué no.

## Ejemplos

### Ejemplo 1. Medir el tiempo de estabilización del sensor

El firmware prende el sensor, lee el ADC cada 50 ms durante 3 segundos, y calcula desde cuándo todas las lecturas quedan a menos de 20 mV del valor final:

```cpp banco-estabilizacion.ino
// nodo (ESP32 clásico): cuánto tarda el sensor de suelo en estabilizarse
constexpr uint8_t PIN_LLAVE_SENSOR = 25;          // bajo = prendido
constexpr uint8_t PIN_SUELO = 34;
constexpr uint32_t PERIODO_MS = 50;
constexpr size_t MUESTRAS = 60;                   // 3 s
constexpr int32_t TOLERANCIA_MV = 20;

uint32_t lecturas[MUESTRAS];

void setup() {
  Serial.begin(115200);
  pinMode(PIN_LLAVE_SENSOR, INPUT);               // apagado
  delay(3000);                                    // demo: que se descargue del todo

  pinMode(PIN_LLAVE_SENSOR, OUTPUT);
  digitalWrite(PIN_LLAVE_SENSOR, LOW);            // prender
  uint32_t inicio = millis();
  for (size_t i = 0; i < MUESTRAS; i++) {
    while (millis() - inicio < i * PERIODO_MS) {
    }
    lecturas[i] = analogReadMilliVolts(PIN_SUELO);
  }
  pinMode(PIN_LLAVE_SENSOR, INPUT);               // apagar

  Serial.println("ms,mV");
  for (size_t i = 0; i < MUESTRAS; i++) {
    Serial.printf("%u,%u\n", static_cast<unsigned>(i * PERIODO_MS), static_cast<unsigned>(lecturas[i]));
  }

  const int32_t valorFinal = static_cast<int32_t>(lecturas[MUESTRAS - 1]);
  size_t desde = MUESTRAS - 1;
  while (desde > 0 && abs(static_cast<int32_t>(lecturas[desde - 1]) - valorFinal) <= TOLERANCIA_MV) {
    desde--;
  }
  Serial.printf("estable desde %u ms (final %d mV)\n",
                static_cast<unsigned>(desde * PERIODO_MS), static_cast<int>(valorFinal));
}

void loop() {}
```

Se recorre desde el final hacia atrás: el instante de estabilización es el primero a partir del cual ninguna lectura se sale de la tolerancia. Se corre varias veces, con varios sensores y en tierra seca y mojada. El valor de `ESTABILIZACION_MS` del firmware del nodo sale del peor caso, con margen.

### Ejemplo 2. 200 ciclos con deep sleep

El nodo repite su ciclo real, más rápido: duerme 2 segundos, prende el sensor, lee, apaga. Cuenta los ciclos, las lecturas inválidas y los brownouts, en NVS:

```cpp banco-ciclos.ino
// nodo (ESP32 clásico): 200 ciclos de la llave del sensor con deep sleep
#include <Preferences.h>

constexpr uint8_t PIN_LLAVE_SENSOR = 25;
constexpr uint8_t PIN_SUELO = 34;
constexpr uint32_t ESTABILIZACION_MS = 1000;
constexpr uint32_t CICLOS_OBJETIVO = 200;
constexpr uint32_t MINIMO_VALIDO_MV = 500;
constexpr uint32_t MAXIMO_VALIDO_MV = 3000;
constexpr uint64_t SUENO_US = 2ULL * 1000000ULL;

Preferences banco;

void setup() {
  Serial.begin(115200);
  banco.begin("banco", false);

  uint32_t ciclos = banco.getUInt("ciclos", 0);
  uint32_t invalidas = banco.getUInt("invalidas", 0);
  uint32_t brownouts = banco.getUInt("brownouts", 0);

  if (esp_reset_reason() == ESP_RST_BROWNOUT) {
    banco.putUInt("brownouts", ++brownouts);
  }

  if (ciclos >= CICLOS_OBJETIVO) {
    Serial.printf("terminado: %u ciclos, %u lecturas inválidas, %u brownouts\n",
                  static_cast<unsigned>(ciclos), static_cast<unsigned>(invalidas),
                  static_cast<unsigned>(brownouts));
    Serial.println(invalidas == 0 && brownouts == 0 ? "PASA" : "NO PASA");
    banco.end();
    return;                                       // se queda despierto mostrando el resultado
  }

  pinMode(PIN_LLAVE_SENSOR, OUTPUT);
  digitalWrite(PIN_LLAVE_SENSOR, LOW);
  delay(ESTABILIZACION_MS);
  uint32_t mv = analogReadMilliVolts(PIN_SUELO);
  pinMode(PIN_LLAVE_SENSOR, INPUT);

  if (mv < MINIMO_VALIDO_MV || mv > MAXIMO_VALIDO_MV) {
    banco.putUInt("invalidas", ++invalidas);
  }
  banco.putUInt("ciclos", ++ciclos);
  Serial.printf("%u,%u\n", static_cast<unsigned>(ciclos), static_cast<unsigned>(mv));
  banco.end();

  Serial.flush();
  esp_sleep_enable_timer_wakeup(SUENO_US);
  esp_deep_sleep_start();
}

void loop() {}
```

Los contadores están en NVS porque un brownout reinicia el chip, y hay que contarlo después. Para empezar otra prueba, se borra el namespace con `banco.clear()` desde otro sketch o se cambia el nombre. Los 200 ciclos tardan unos 10 minutos.

### Ejemplo 3. 20 arranques del teclado del taller

Para el control de acceso de la [E.4](/conceptos/e-4), el criterio es: en 20 arranques, el teclado enumera siempre, y se anota el peor tiempo desde que se prende VBUS. El firmware mide el tiempo, lo guarda y se reinicia solo:

```cpp banco-enumeracion.ino
#include <Preferences.h>
#include <USBHost.h>
#include <USBHostHIDKeyboard.h>

constexpr uint8_t PIN_VBUS = 5;
constexpr uint32_t ARRANQUES_OBJETIVO = 20;
constexpr uint32_t LIMITE_MS = 5000;
constexpr uint32_t DESCARGA_MS = 1000;

USBHostHIDKeyboard teclado;
Preferences banco;
uint32_t vbusDesde = 0;

void terminarArranque(bool enumero, uint32_t ms) {
  uint32_t arranques = banco.getUInt("arranques", 0) + 1;
  banco.putUInt("arranques", arranques);
  if (!enumero) {
    banco.putUInt("fallas", banco.getUInt("fallas", 0) + 1);
  } else if (ms > banco.getUInt("peor_ms", 0)) {
    banco.putUInt("peor_ms", ms);
  }
  Serial.printf("arranque %u: %s en %u ms\n", static_cast<unsigned>(arranques),
                enumero ? "enumeró" : "NO enumeró", static_cast<unsigned>(ms));
  banco.end();
  digitalWrite(PIN_VBUS, LOW);
  delay(DESCARGA_MS);
  ESP.restart();
}

void setup() {
  Serial.begin(115200);
  pinMode(PIN_VBUS, OUTPUT);
  digitalWrite(PIN_VBUS, LOW);
  banco.begin("banco", false);

  if (banco.getUInt("arranques", 0) >= ARRANQUES_OBJETIVO) {
    Serial.printf("terminado: %u fallas, peor tiempo %u ms\n",
                  static_cast<unsigned>(banco.getUInt("fallas", 0)),
                  static_cast<unsigned>(banco.getUInt("peor_ms", 0)));
    banco.end();
    return;
  }

  teclado.registerWithHost();
  if (!USBHost.begin()) {
    terminarArranque(false, 0);
  }
  digitalWrite(PIN_VBUS, HIGH);
  vbusDesde = millis();
}

void loop() {
  if (!USBHost.started()) return;                 // prueba terminada
  USBHost.task();
  uint32_t ms = millis() - vbusDesde;
  if (teclado.mounted()) {
    terminarArranque(true, ms);
  } else if (ms >= LIMITE_MS) {
    terminarArranque(false, ms);
  }
}
```

`ESP.restart()` prueba el arranque del firmware, pero no un corte de alimentación: la fuente y los capacitores no se descargan del todo. Por eso, además de esta prueba, se hacen 20 arranques cortando la fuente a mano. Si los dos dan bien, el orden de arranque con la llave está probado.

## Errores comunes

### Criterios que no se pueden medir

"Funciona bien", "arranca rápido", "no se calienta". Cada criterio necesita un número y una forma de medirlo.

### Escribir los criterios después de probar

Si el criterio sale de lo que dio la prueba, la prueba siempre pasa.

### Probar pocas veces

Dos arranques no prueban nada sobre una falla de 1 en 10. La cantidad de repeticiones sale de qué tan rara es la falla que querés descartar.

### Contar fallas en memoria que se borra

```cpp
// Mal: un brownout reinicia el chip y el contador se pierde
uint32_t brownouts = 0;

// Bien: en NVS, que sobrevive a cualquier reinicio
banco.putUInt("brownouts", ++brownouts);
```

### Probar solo en las mejores condiciones

Batería llena, un solo sensor, temperatura de oficina. En el campo, la batería baja, los sensores varían y el sol calienta la caja.

### Ajustar un número sin entender el resultado

Si un arranque tarda diez veces más que el resto, subir el límite lo esconde. Primero se averigua por qué.

## Resumen

- Una prueba en banco usa el equipo real contra criterios escritos antes: qué se hace, cuántas veces y qué cuenta como falla.
- Las fallas intermitentes necesitan repeticiones: con una falla de 1 en 10, 20 intentos todavía tienen un 12 % de no verla.
- Un firmware de banco repite el trabajo, cuenta las fallas en NVS (sobrevive a los reinicios) y muestra los resultados en CSV.
- Se prueba en varias condiciones y con varias piezas, no solo en las mejores.
- `ESP.restart()` no reemplaza un corte de alimentación; las dos pruebas hacen falta.
- Cada resultado raro se investiga antes de ajustar un número.
